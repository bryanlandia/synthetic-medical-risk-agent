# Design

## Context

See proposal.md. Today `web/components/Demo.tsx` holds four tabs; `ChartTab.tsx` shows one of four patients from `web/content/demo_patients.json` (built by `evals/src/evals/demo_patients.py` from fixed rules over dev) with `ReportCard` beside it and `PacketPanel.tsx` underneath. `/api/packet` and `/api/analyze` forward to the agent with the secret server-side (`web/lib/forward.ts`); `/api/packet` already accepts `{message, attestations}` and returns the criteria, evidence, gaps, summary, source and the risk report. Styling is 99 lines of plain CSS. Analytics (`Analytics.tsx`) counts clicks on elements carrying `data-track` from a fixed name set (`web/lib/analytics.ts`). The Playwright suite (74 tests) drives the tab layout and four patients. Policy v2 gives 33 C1-met patients in dev.

## Goals / Non-Goals

**Goals:** a supervisor's worklist that reads like a product; a clear statement of what the packet is for; a restrained, consistent Material look; honest, quiet demo notes; no change to the service, the packet logic or the frozen evals.

**Non-Goals:** accounts, a shared database or any server-side state; a simulated payer response; editing the preparer's answers; dark mode; a mobile-first layout; changes to the policy, the note reader, the packet prompt or the evals.

## Decisions

- **Material UI (MUI), pinned.** `@mui/material`, `@emotion/react`, `@emotion/styled` and `@mui/material-nextjs` (App Router cache provider), exact versions checked for React 19 and Next 15 peer ranges when the task is done. MUI is Material Design 2 in components; the newer Material 3 look is approximated through one custom theme (palette, type scale, rounded shapes), not a separate library. Google's Material Web components are in maintenance mode, so not chosen. Alternative: keep plain CSS, which would not give the polished, friendly look asked for. Fonts: the system stack with Roboto first; no web-font fetch (the spec forbids third-party fonts and builds must not need the network for fonts). Icons: a handful of inline SVG, not the full icon package, to keep the bundle small.
- **The packet is explained three ways, none of them modal.** A "What is this packet for?" card on the queue (dismissible, persisted, restored by Reset), a help dialog from every case with the same text, and tooltip hints on four terms at first use. One source string for the text, used by all three, so they cannot drift; a test searches it for the banned verdict words.
- **State: a small reducer persisted to `localStorage`.** Key `vk-review-v1` holds `{casesHash, policyId, dismissedIntro, cases: {id: {status, packet?, note?, rationale?, events[]}}}`. On load, a mismatch of `casesHash` or `policyId` discards it. The packet result (about 8 KB) is stored per opened case, so reopening makes no request and the whole queue stays under 300 KB. Reset clears the key. Nothing is written server-side. A statically rendered page hydrates the saved state after mount, so the server and first client render agree (the queue shows its default state for a moment, then the saved one).
- **One packet call per case, on first open.** `/api/packet` already returns the report, so `/api/analyze` is not used in the flow. With 10 requests a minute and 200 a day per visitor, working 30 cases uses at most 30. Answers are the preparer's, from the cases file; the supervisor cannot edit them (assumption: a real supervisor reviews what was attested, and editing would need a second request and summary call per change). If a retry is needed after a 429 or 503, the case stays un-fetched.
- **Release gating is plain rules over the packet's statuses.** Unknown blocks Release (a gap needs the preparer, so Return is offered); unmet requires the supervisor's own rationale of at least 20 characters; all met releases directly. Return needs a note of at least 5 characters; Close needs nothing. The tool never fills in or edits either text.
- **The cases file is built in `evals`, replacing the demo-patient builder.** `evals demo-cases` reuses the chart building (reference ranges and flags after unit conversion) and the harness's `render_message`, selects 30 dev records by strata with a seeded draw (its own seed stream), and writes the preparer answers, insurer, preparer, time and request code by the same stream. Strata come from the independent packet reference (C1 and C2 statuses) and the record's noise tags, so no ground truth is read into the file. `web/content/demo_patients.json` and `evals demo-patients` are removed; the lab names the free-text view needs come from the cases file. Preparer answers are a separate seeded draw from the eval attestation fixtures (which are uniform and would leave almost no case fully answered), and the eval fixtures are untouched.
- **Fictional names are generated, short and obviously invented.** Ten insurer names in a committed list (each shown with "(fictional)"), eight made-up preparer surnames with no credentials, request codes `VK-PET-` plus five digits, received times within one working day, shown as times only.
- **Demo notes are one component.** A `DemoNote` (chip plus muted text) takes its text from a single table, used wherever a simulated element appears, so the set in the spec is checkable by a test that opens each place. The persistent strip is a fixed bar. The notes are not dismissible banners and sit beside the thing they describe.
- **Analytics.** New fixed names (`nav:queue`, `nav:free`, `nav:card`, `nav:about`, `case:NN`, `filter:status`, `release`, `return`, `close`, `confirm`, `reset_demo`, `help`, `sent_message_expander`, `packet_copy`, `packet_print`, `example:<slug>`, `send_free_text`, `link:<host>`), validated by the existing name checker; no patient id, status or text is ever in an event. The opt-out and Do Not Track behavior are unchanged.
- **Print.** A print stylesheet shows only the released packet and the notice; the dialogs and queue are hidden.
- **Reproducibility, cost and secrets.** The cases build is seeded and byte-identical on regeneration, with a stale-file test. New dependencies are pinned and installed with `--ignore-scripts`. No model spend in tests (scripted service); an optional live smoke check of one case is a few cents. No new secret or variable; the browser still never holds the secret or the service address.

## Risks / Trade-offs

- [MUI and Emotion add weight and a flash of unstyled content with a static page] → measure the built JS size before and after, use the App Router cache provider, and fail the task if first-load JS grows past an agreed budget set when measured; keep the icon set tiny.
- [Rewriting the UI breaks most of the 74 web tests] → restructure the suite as part of the change: keep the forward and packet-forward tests, rewrite the demo tests around the queue and case view, and keep the analytics and wording tests updated to the new names.
- [A fully scripted preparer makes the demo feel canned] → the demo notes say so plainly, and the 30 cases vary in what is met, unknown and unmet.
- [localStorage holds the supervisor's typed text] → it stays on the visitor's device, is never sent or counted, and Reset clears it; the notice says it is saved in this browser only.
- [The intro panel could read as marketing] → plain words, no figures, no savings; a test searches the flow for dollar amounts and accuracy figures.
- [The word "release" being read as a coverage decision] → the dialog says nothing is transmitted and that the insurer's response is not simulated.
